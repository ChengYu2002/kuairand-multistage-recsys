## 1. 两个核心研究问题

1. **Negative Sampling Study** — 负样本的**来源**（random / in-batch / in-batch+logQ /
   exposure / hybrid，§7.1）与**数量**（10 个 vs 完整 in-batch 的 1023 个，§7.3）
   如何影响双塔召回在全库检索中的效果？
2. **Multi-Task Learning + Selective Sharing** — 在不同任务稀疏度与可比参数预算下，
   不同共享机制（Single-Task / MMoE / CGC / PLE / Selective Sharing）如何影响正迁移与负迁移？

## 2. System Architecture

```text
Raw KuaiRand Logs
        ↓
Feature / Data Pipeline        (user sampling → temporal split → T-1 snapshots)
        ↓
Multi-channel Retrieval        (Two-Tower / ItemCF —— 见下方说明)
        ↓
[Optional] Coarse Ranking      (LightGBM, P1)
        ↓
Multi-task Fine Ranking        (Single-Task / MMoE / CGC / PLE / Selective Sharing)
        ↓
Score Fusion → Re-ranking
        ↓
Offline Evaluation
```

架构是完整链路，但离线实验**不要求所有阶段 end-to-end 串联训练**，分为
Track A (Retrieval) 与 Track B (Ranking & Multi-task) 两条轨道。

> **关于 candidate union**：上图是工业链路的完整形态，真实系统会把多路召回合并成
> 一个候选集再交给排序。但本项目**不用 union 产出任何上报的召回指标**，每一路召回
> 都在同一个候选库上独立评估。原因是研究问题一要比较不同负采样策略对双塔的影响 ——
> 一旦把 ItemCF 的结果并进候选集，双塔的 Recall 就不再可归因，策略间的差异会被另一路
> 召回的贡献掩盖。ItemCF 在本项目中的定位是**经典非神经基线**，不是召回源。
> Track B（排序与多任务）在打过标的曝光日志上训练与评估，也不消费 union，因此
> union 目前没有实现，且不是 P0 交付物。

## 4. Leakage Control

严格区分 **prediction-time feature** 与 **post-interaction outcome**。
播放时长、主页/评论区停留时长、是否进入主页等曝光后行为**只能作为 label 或分析对象**。
官方每日统计文件不直接作为特征，统一从 past-only logs 自建。

> Note: snapshot-style user features (follow / fan counts 等) may contain limited future
> information relative to earlier interactions.

## 5. T-1 Feature Pipeline

Day T 的样本只允许使用 **Day T-1 及更早**日志生成的聚合特征，按
`user+date` / `item+date` / `author+date` / `tag+date` 预聚合后按日期 join 回样本。

## 6. Candidate Catalog & Request Unit

- **Protocol A — Warm Catalog**：只含 **train 段**出现过、且曝光次数达到频次门槛的 item。
  不含 warmup 与 valid：valid 保持干净调参集的身份。口径与实测规模（KuaiRand-1K）：

  | 协议 | 门槛 | 候选库 item | 有效 request | request 覆盖率 |
  |---|---|---:|---:|---:|
  | 主协议 | `train_freq >= 5` | 194,310 | 66,536 | 12.1% |
  | 辅助协议 | `train_freq >= 1` | 1,708,902 | 120,415 | 21.9% |

- **Protocol B — Time-aware Available Catalog**：允许 `upload_date < request_date` 的未见新
  item（`upload_dt` 仅日期粒度，故为严格小于）。**尚未实现**。
- **Request Unit**：测试窗口内**每一个正向点击 / 有效播放事件**（`is_click or long_view`）
  = 一个 retrieval request。测试窗共 550,316 个正向事件，其中 66,536 个的目标 item 落在
  主协议候选库内。注意 66,536 个事件只对应 51,746 个不同的 `(user, time_ms)` 查询时刻 ——
  一次请求返回一批视频，用户可能点击其中多个，这些事件共享同一份查询上下文。

> 必须与 Recall 一并披露的限制：频次门槛使候选库偏向较热门 item，主协议仅覆盖 12.1%
> 的测试正向事件。这个低覆盖率有**两层成因，不能只归给门槛，也不能说与门槛无关**：
>
> 1. 门槛本身让覆盖率从 21.9% 降到 12.1%，即少掉 53,879 个 request（9.8 个百分点）；
> 2. 21.9% 这个**上限**则来自 Protocol A「训练期必须见过」的前提 —— 测试期 78.1% 的
>    正向事件，其目标 item 在训练段一次都没出现过（本数据集 72.6% 的视频是 31 天窗口
>    期内上传的，内容换代极快）。
>
> 也就是说：调门槛最多把覆盖率拉回 21.9%，再往上只能靠 Protocol B + 带 side feature
> 的物品塔。
>
> The sampled catalog is an offline approximation and inherits selection bias from the
> sampled users and logged exposures.

## 7. Results

### 7.1 Negative Sampling (Two-Tower)

**非神经基线（双塔必须跨过的地板）** —— Protocol A，66,536 条考题，按 request 平均：

| Baseline | Recall@50 | Recall@100 | Recall@500 | NDCG@100 |
|---|---:|---:|---:|---:|
| Random guess | — | 0.000515 | — | — |
| **Popularity** | **0.00222** | **0.00490** | **0.02301** | **0.00101** |
| ItemCF-50（主基线） | 0.00095 | 0.00150 | 0.00942 | 0.00036 |
| ItemCF-50-IUF（消融） | 0.00092 | 0.00167 | 0.00899 | 0.00038 |
| ItemCF-All（消融） | 0.00005 | 0.00017 | 0.00532 | 0.00003 |

观察记录（非实现缺陷，已由 19 项独立验算排除实现错误）：

- **标准余弦 ItemCF 在本数据上低于热度基线。** 机制是极稀疏共现下的冷门偏置：每个
  item 平均只被 6.2 个用户看过，绝大多数共现次数为 1，`|Ui∩Uj| / √(|Ui||Uj|)` 的分子
  近似常数，排序几乎完全由分母决定，于是余弦退化成「谁更冷门谁排前面」。实测
  ItemCF-50 的 Top-100 中位 `train_freq` = 7，而考题答案中位 = 14、候选库全体中位 = 8
  —— 推荐分布与目标分布方向相反，因此可以低于随机猜测。
- **历史越长反而越差**（ItemCF-All < ItemCF-50）：历史从 50 条放大到中位 4,271 条后，
  被翻出来的超冷门 item 更多，冷门偏置被进一步放大。
- **IUF 影响很小且方向不一致**（@100 略升、@500 略降），不进主线。
- **UserCF 一次性诊断**：R@100 ≈ 0.0087（静态用户画像口径，未做正式实现与验算），
  用于确认协同信号确实存在、排除「CF 在本数据上全盘失效」。因「最相似用户」这一量
  在 1,000 用户抽样下被抽样本身扭曲（而 item-item 共现是物品目录的真实属性，样本量
  增大会收敛），UserCF 不进主线，仅作记录。

必须与上表一并披露的口径：

- **补位**：ItemCF-50 有 **13.28%** 的查询时刻非零候选不足 500，尾部由 `pad_order`
  （默认 `catalog_asc`，热门优先）填充，这部分 Top-K 不由 ItemCF 决定。改用
  `catalog_desc` 时 Recall@500 约差 5%（0.00942 vs 0.00894）。
- **不排除已看视频**：为使各召回方法的后处理完全一致，一律不排除用户历史视频。
  代价是热度基线 Top-50 中有 26.3% 是该用户训练期已曝光的项。
- **查询单位**：66,536 条考题只对应 51,746 个不同的 `(user_id, time_ms)`；同一时刻的
  考题共享同一份 Top-K。

**五个实验臂对比** —— 同一候选库、同一考题集、除负采样外所有变量固定（§16.6）。
其中 **In-batch + logQ** 与 In-batch 的唯一差异是 loss 里的 logQ 校正，采样器本身同一个类。
20,000 步，embedding_dim 64，temperature 0.05，10 负样本/正样本，item tower = ID-only。
**3 seeds（42/43/44），mean ± std，按 request 平均**；汇总由
`python -m src.evaluation.negative_sampling_analysis` 复现：

| Strategy | Recall@50 | Recall@100 | Recall@500 | 倍热度基线(@100) | 末 100 步 loss |
|---|---:|---:|---:|---:|---:|
| **Random** | **0.00488±0.00027** | **0.00883±0.00017** | **0.03481±0.00073** | **1.80x** | 0.2448±0.0032 |
| **In-batch + logQ** | **0.00543±0.00063** | **0.00997±0.00071** | **0.03806±0.00205** | **2.03x** | 0.3128±0.0119 |
| In-batch | 0.00288±0.00021 | 0.00558±0.00036 | 0.02463±0.00114 | 1.14x | 0.2922±0.0080 |
| *Popularity 基线* | *0.00222* | *0.00490* | *0.02301* | *1.00x* | — |
| Hybrid (5 Random + 5 Exposure) | 0.00183±0.00013 | 0.00350±0.00024 | 0.01525±0.00055 | 0.71x | 0.2635±0.0149 |
| Exposure | 0.00023±0.00005 | 0.00046±0.00001 | 0.00227±0.00019 | 0.09x | 0.0788±0.0111 |

两行都加粗是故意的：**Random 与 In-batch + logQ 是并列的头两名，它们之间的先后没有
被这 3 个 seed 定下来**（见下面的配对表，logQ 对 Random 的差值是 12 格里最弱的一档）。
`loss` 一列**跨臂不可比** —— 负样本来自不同分布时它衡量的是不同难度的题（logQ 把热门
item 的 logit 压低，题变难，loss 自然更高；它只能看同一臂内是否收敛）。

配对差值（同 seed 相减，seed 是受控的区组因子）：

| vs Random | Recall@50 | Recall@100 | Recall@500 | 方向一致性 | `\|mean\|/std` @100 |
|---|---:|---:|---:|---|---:|
| **In-batch + logQ** | **+0.00055±0.00037** | **+0.00114±0.00060** | **+0.00325±0.00147** | 3/3 同号 | 1.9 |
| In-batch | −0.00200±0.00031 | −0.00325±0.00030 | −0.01018±0.00135 | 3/3 同号 | 10.9 |
| Hybrid | −0.00306±0.00014 | −0.00533±0.00011 | −0.01956±0.00075 | 3/3 同号 | 46.8 |
| Exposure | −0.00466±0.00028 | −0.00838±0.00017 | −0.03254±0.00055 | 3/3 同号 | 49.6 |

logQ 臂的受控对照是 In-batch（唯一差异就是那一项校正），不是 Random：

| vs In-batch | Recall@50 | Recall@100 | Recall@500 | 方向一致性 | `\|mean\|/std` @100 |
|---|---:|---:|---:|---|---:|
| **In-batch + logQ** | **+0.00255±0.00066** | **+0.00439±0.00085** | **+0.01343±0.00174** | 3/3 同号 | 5.2 |

12 格全部 3/3 同号，但强弱差了一个数量级：`|mean|/std` 从 59.2（Exposure 的崩溃）
到 **1.5~2.2（logQ 臂超过 Random 的那一档）**。所以这里只说「logQ 臂把 In-batch 从
1.14x 修到 2.03x，`|mean|/std` 3.9~7.7」，**不说它已被证明优于 Random** —— 后者是 12 格
里最弱的一档，3 个 seed 撑不住这个结论。不打「显著/不显著」标记 —— 3 个 seed 估出的
std 本身不可靠（§26）。

**主结论：负样本分布有两个独立的性质，必须分开看 —— 覆盖度封顶，偏差可修。**

    In-batch+logQ 2.03x > Random 1.80x > In-batch 1.14x > 热度基线 1.00x
                                       > Hybrid 0.71x > Exposure 0.09x

- **覆盖度是硬上限。** Exposure 的 proposal 只在每个用户**自己**的曝光集合里（中位
  641 个 item），Hybrid 有一半如此 —— 它们封在 0.71x / 0.09x，训练目标和「从 19.4 万
  里挑」根本不是同一道题。这类缺陷**不是校正能救的**。
- **偏差是可修的。** In-batch 的 proposal 正比于训练正样本频率，覆盖候选库的
  **96.5%**（187,552/194,310，由 logQ 的 Q 表实测）—— 它从来不缺覆盖度，缺的是对这个
  已知 proposal 的校正。加上 logQ 后同一个采样器从 1.14x 变成 2.03x。

> **这一条修正了本节四臂时期的结论。** 原文写的是「负样本的『候选库覆盖度』比『难度』
> 重要得多」。第五臂证明那句话把两件事混在了一起：它对 Exposure / Hybrid 成立，但把
> In-batch 的 1.14x 一并归给了覆盖度，而那其实是一个**可修的偏差**。四个点看不出这个
> 区别 —— 能看出来是因为补了一个只改校正项、不改采样器的受控臂。

**In-batch 的采样偏差被量出来了，而且修回来了。** 未校正时它整体只比「给所有人推同一份
榜单」高 14%（@100）、7%（@500）；但 §7.2 的频次分层显示这不是均匀变差，而是一次
**用 warm 换 tail** 的交易：

    R@100 倍随机猜      tail      mid     warm
    Random              5.7x     15.3x    36.8x
    In-batch           10.6x     12.9x     7.6x
    In-batch + logQ      6.7x     17.8x    40.1x

In-batch 在 tail 层（`train_freq` 5~9）**反超 Random 1.85 倍**（0.00544 vs 0.00294），
却在 warm 层只剩 Random 的 **20.5%**（0.00389 vs 0.01893）。成因是**热门 item 被过度
惩罚**：in-batch 的负样本概率正比于该 item 的正样本频率，于是越热门的 item 被压低的
次数越多。这与「学到了全局热度排序」恰好相反 —— 实测 `ū·v_i` 与 `train_freq` 的
Spearman ρ 从 Random 的 **+0.519** 降到 In-batch 的 **+0.200**，热度分量被削弱而非强化。

**logQ 校正把这笔交易反向做了一次，方向与事先写死的预测一致。** 从每个候选 logit
（**含正样本**）里减去 `log Q(item)`，Q = 该 item 在训练正样本里的全局频率：

| logQ − In-batch（同 seed 相减，R@100） | 每 seed 差值 | mean±std | 方向 | `\|mean\|/std` |
|---|---|---:|---|---:|
| tail | −0.00168 / −0.00238 / −0.00185 | −0.00197±0.00037 | 3/3 同号 | 5.4 |
| mid | +0.00329 / +0.00175 / +0.00243 | +0.00249±0.00077 | 3/3 同号 | 3.2 |
| **warm** | +0.01902 / +0.01619 / +0.01506 | **+0.01676±0.00204** | 3/3 同号 | 8.2 |

warm 从 7.6x 回到 **40.1x**（名义上高过 Random 的 36.8x，但这一格对 Random 的配对差值
是 +0.00172±0.00153、`|mean|/std` 仅 1.1 —— 3/3 同号，不足以定先后），tail 从 10.6x 退回 6.7x ——
in-batch 的 tail 优势本来就是同一个偏差的另一面，修掉偏差它自然一起退。学到的热度
分量同步回升：ρ 从 **+0.200** 回到 **+0.379**（3 seeds，std 0.004）。

> **这组数字是对照事先写死的预测验的，不是事后解释。**
> `results/logq_prediction.json` 写于 2026-10-29 20:43，在 `inbatch_logq` 跑第一个正式
> seed 之前；里面列了主预测、次预测，以及一条**证伪条件**：「warm 层不回升（或反而更
> 低），则机制诊断错误 —— 那比任何新数字都值得记录」。事后逐条对账：warm 回升 ✓、
> ρ 回升 ✓、「tail 的 10.6x 可能回落」✓（10.6x → 6.7x）、「overall 上升但**不保证**超过
> Random」✓（0.00558 → 0.00997，确实超过了，而预测明确留了不超过的余地）。
> 五条可测预测全中。这条机制链（频次分层 → 定位过度惩罚 → logQ → warm 回升）因此
> 不是一个能随结果改口的故事。

**Exposure 单独使用会摧毁全库召回，机制已定位。** 它的 Recall 只有 Random 的 5.2%，
比热度基线还低一个数量级，而它的 loss 却低一个量级（0.079 vs 0.245）——
这是「训练目标与评估任务错配」最干净的证据：模型把「在这个用户看过的约 641 个视频里
挑出他点过的那个」学得极好，而评估问的是「从 19.4 万里挑」。

> 它：脚本的 `--check` 校的是它自己的冻结基准，旧数字只作并列参考打印。
> （教训：一个进了 README 的数字，没有脚本就等于没有。）

下面两组仍是探索性诊断（单 seed；原始诊断脚本未纳入仓库），用于解释现象，不作判据：

| 量 | Random | In-batch | Hybrid | Exposure |
|---|---:|---:|---:|---:|
| 推荐 Top-100 的 `train_freq` 中位 | 15 | — | 11 | 8 |
| 物品向量的全局分量占方差 | 0.0852 | 0.0463 | 0.0330 | 0.0245 |

`ū·v_i` 是「与用户无关的那一份得分」。**Exposure 学出来的全局分量与热度负相关** ——
它主动偏好冷门视频，推荐分布（中位 `train_freq` 8）塌到候选库自身的分布（8）上，
而考题答案的中位是 14、Random 的推荐中位是 15。成因是曝光负样本的采样概率正比于
「有多少用户被推过它」，而热门视频被推给更多人，于是热门视频被系统性地多压 ——
实测 `p_exposure` 与正样本频率的 Spearman ρ = 0.286。全库召回最需要的那个
「这个视频普遍值得推」的先验，被它学成了负的。

> **两个被否掉的假设，记录在此以免重走。**
> ① 「大量 item 从没当过负样本因而霸榜」—— 否：曝光池覆盖候选库的 97.9%，
> 零负样本的只有 4,125 个。
> ② 「曝光负样本抵消了热度信号」—— 否：`pos/neg` 比值的动态范围在 Exposure 下反而
> 更大（119.8%）。该量被冷门 item 的噪声主导，**量错了对象**；正确的对象是模型
> **学出来的**全局分量。

> **最后一行（全局分量占方差）与 Recall 严格单调，但不作判据。** 它是 4 个点、
> 1 个 seed 上的观察，且缺一个「为什么是这一列而不是 ρ」的机制解释 —— 注意 Hybrid 的
> ρ（+0.469）接近 Random（+0.519），Recall 却差一倍多，说明热度先验不是全部。
> logQ 臂更直接地说明了这一点：它的 ρ（+0.379）**低于** Hybrid，Recall 却高 2.8 倍。
> 作为观察记录保留，补足 3 seeds 之前不进结论。

**自然的后续实验：扫混合比例。** 当前只证明了 `hybrid_mix = 0.5` 在这个设置下过重，
不能外推为「任何 Hybrid 都无效」。扫 0.05 / 0.1 / 0.2 / 0.5 能给出转折点，比再加一种
策略更有信息量。未做。

> ⚠️ **§16.6 可比性：有一层保护是空的。** 结果 JSON 只记录了 `strategy / seed /
> protocol / item_tower_config / steps / loss_tail / metrics`。`lr`、`batch_size`、
> `negatives_per_positive`、`temperature`、`optimizer` **未逐次落盘**，无法事后断言
> 它们在 15 次训练间相同 —— 排序侧有 `input_fingerprint` 挡着，召回侧没有这个机制。
> **已确认（由权重形状复原）**：15 个 checkpoint 的参数张量名字与形状逐一相同，
> `catalog_range` 与 `steps` 一致，这覆盖了架构、`embedding_dim`、两座塔层宽与
> `share_item_embedding`。
> **已知缺口**：`configs/retrieval.yaml` 最后写入 2026-09-25 23:51，晚于 Random /
> In-batch 的 seed 42 跑完时间（21:07 / 21:52）。那两次用的配置无法从 git 复原
> —— 同一个提交里既新增了键又改写了注释，提交内的时间线不存在。
> 由于 `two_tower.py` 缺 `temperature` / `train_target_scope` 会直接 KeyError，
> 那两次跑时这些键必然已存在；但「必然存在」不等于「值相同」，故如实记录为缺口。

> ⚠️ **Exposure 的 fallback**：空池子用户 9/1,000（0.90%），但逐行实测 fallback
> 仅 **47/20,480,000 = 0.00023%** —— 那 9 个用户中只有 2 个在训练段出现过，共贡献
> 3 条训练正样本。Exposure 实际上是纯的，上述崩溃与 fallback 无关。
> 比例随结果落盘（checkpoint 的 `sampler` 字段），可独立核对。

训练与评估口径：正样本取 train 段正向事件且目标落在候选库内（121 万条，占全部正样本
的 58%）。**正负样本必须同空间** —— 若正样本可在词表任意位置而负样本只来自候选库，
「不在候选库」就完美预测「是正样本」（占 42%），而成员身份恰好由 index 区间编码。

### 7.2 Item Tower / Cold Start

**Protocol A 按构造没有 cold item，这一列填不出来。** 候选库的定义是「train 段出现过
且 `train_freq >= 5`」，实测候选库 `train_freq` 最小值就是 5，66,536 条考题的答案
**全部**落在候选库内（库外 0 条）。冷启动需要 Protocol B（time-aware available
catalog，含训练期从未出现的 item），而 `catalog.upload_rule` 标着「Protocol B 用，
未实现」。§6 记录的天花板正来自这里 —— 测试期 **78.1%** 的正向事件，其目标 item 在
训练段一次都没出现过，这些事件连考题都进不了。本节量的是**剩下 21.9% 内部的频次
梯度**，不是冷启动，两者不能混。

**频次分层口径**（切点在看到任何 Recall 之前定好，之后未调整）。按**考题答案**的
`train_freq` 切三段，用绝对值而非分位数 —— 分位数会随候选库变化（aux 协议
`min_train_freq=1`、将来的 Protocol B），那样跨协议不可比：

| band | `train_freq` | 考题数 | 占比 |
|---|---|---:|---:|
| tail | 5 ≤ f < 10 | 22,675 | 34.1% |
| mid | 10 ≤ f < 30 | 27,928 | 42.0% |
| warm | f ≥ 30 | 15,933 | 23.9% |
| *cold* | *未在 train 出现* | *0* | *Protocol A 不含* |

**分母必须是随机猜，不能是热度基线。** 实测热度基线在 tail 与 mid 层**恒为 0**，
且这是结构性的：热度 Top-500 全部是 `train_freq >= 114` 的 item，按定义都在 warm 层，
永远打不中 tail/mid 的答案（它的全部战绩来自 24% 的 warm 考题，warm R@100 = 0.02046）。
随机猜才与层无关：每条考题一个答案，随机取 K 个命中的概率是 `K/194,310`
（@50/100/500 = 0.000257 / 0.000515 / 0.002573）。

**ID-only 物品塔，五个实验臂 × 3 seeds，R@100 per_request（倍随机猜）**
—— 由 `python -m src.analysis.cold_start_analysis` 复现：

| Strategy | tail R@100 | mid R@100 | warm R@100 | tail / mid / warm 倍随机猜 |
|---|---:|---:|---:|---|
| **Random** | 0.00294±0.00052 | 0.00785±0.00025 | **0.01893±0.00076** | 5.7x / 15.3x / **36.8x** |
| **In-batch + logQ** | 0.00347±0.00033 | **0.00915±0.00090** | **0.02065±0.00203** | 6.7x / **17.8x** / **40.1x** |
| In-batch | **0.00544±0.00064** | 0.00666±0.00038 | 0.00389±0.00085 | **10.6x** / 12.9x / 7.6x |
| Hybrid | 0.00257±0.00025 | 0.00442±0.00060 | 0.00322±0.00020 | 5.0x / 8.6x / 6.3x |
| Exposure | 0.00056±0.00014 | 0.00043±0.00006 | 0.00036±0.00025 | 1.1x / 0.8x / 0.7x |

四条读得出来的结论：

- **Random 的优势全部来自 warm 层，且随频次单调上升**（5.7x → 15.3x → 36.8x）。
  它学到的是正确方向的热度先验。
- **In-batch 是一次 warm 换 tail 的交易**，不是均匀变差：tail 层反超 Random 1.85 倍，
  warm 层只剩 20.5%。方向与「in-batch 偏向热门」的直觉相反，机制见 §7.1。
- **logQ 把这笔交易反向做了一次**：warm 7.6x → 40.1x，tail 10.6x → 6.7x，三层的配对
  差值都 3/3 同号（§7.1 有逐 seed 的表）。**这一层正是频次分层的价值所在** —— overall
  R@100 从 0.00558 到 0.00997 只说明「变好了」，说不出好在哪一层、代价付在哪一层，
  而机制诊断要的恰恰是后者。
- **Exposure 在三层上全都约等于随机猜**（0.7x ~ 1.1x），没有层内优势可言 ——
  它不是「偏向某一层」，是整体不含信息。

**ID + Side 物品塔（3 seeds）** —— 受控对比只有一个自变量：物品塔是否吃侧信息
（author / tag / duration / video_age）。**两侧的负采样都固定在 In-batch + logQ**，
所以这里的 ID-only 行必须是五臂表里的 logQ 那一行，不能拿 Random 那一行来比
（否则同时差了物品塔与负采样来源，无法归因）：

| Item Tower（均为 In-batch + logQ） | Recall@50 | Recall@100 | Recall@500 | 倍热度基线(@100) |
|---|---:|---:|---:|---:|
| ID-only | 0.00543±0.00063 | 0.00997±0.00071 | 0.03806±0.00205 | 2.03x |
| **ID + Side** | **0.00590±0.00032** | **0.01106±0.00040** | **0.04249±0.00068** | **2.26x** |

| band R@100（倍随机猜） | tail | mid | warm |
|---|---:|---:|---:|
| ID-only | 0.00347（6.7x） | 0.00915（17.8x） | 0.02065（40.1x） |
| **ID + Side** | **0.00456（8.9x）** | **0.01038（20.2x）** | **0.02151（41.8x）** |

配对差值（同 seed 相减，seed 是受控的区组因子）：

| ID+Side − ID-only | mean±std | 方向一致性 | `\|mean\|/std` | 相对 |
|---|---:|---|---:|---:|
| overall R@50 | +0.000471±0.000948 | 2/3 同号 | 0.50 | +8.7% |
| overall R@100 | +0.001092±0.000948 | 3/3 同号 | 1.15 | +11.0% |
| **overall R@500** | **+0.004424±0.001790** | 3/3 同号 | **2.47** | +11.6% |
| **tail R@100** | **+0.001088±0.000533** | 3/3 同号 | **2.04** | **+31.4%** |
| mid R@100 | +0.001229±0.001451 | 3/3 同号 | 0.85 | +13.4% |
| warm R@100 | +0.000858±0.001534 | 2/3 同号 | 0.56 | +4.2% |

> **这是一条事先写死、可从 git 查证的预测，它站住了。** 上一版 README 写的是「预期它的
> 增益应集中在 tail 层 —— 低频 item 的 ID embedding 只吃到 5~9 次梯度，而侧信息是跨
> item 共享的」，提交于 `ebe0e86`（2026-10-29 19:48），而三个 seed 落盘是 10-30 的
> 01:23 / 02:02 / 02:42 —— 预测早于第一份数据 5.5 小时，不是事后解释。
> 事后对账：tail 是六格里**唯一**既拿到最大相对增益（**+31.4%**）又拿到最强方向性
> （`|mean|/std` **2.04**）的分层格；warm 只 +4.2% 且 2/3 同号。机制与预期一致 ——
> `train_freq` 5~9 的 item，它的 ID embedding 一共只吃到 5~9 次梯度，而 author / tag /
> duration / video_age 是跨 item 共享的参数，低频 item 借得到高频 item 的更新。

> ⚠️ **「整体提升 11%」这句话比分层结论弱，不进结论。** overall R@100 的
> `|mean|/std` 只有 **1.15**，比 §7.1 里明确拒绝下结论的那一格（logQ 臂超过 Random，
> 1.9）还低。六格里够干净的只有 overall R@500（2.47）与 tail R@100（2.04）。
> 按本项目口径：**侧信息在 tail 层的增益可以写进结论，「整体 +11%」只作记录。**
> 不打显著/不显著标记 —— 3 个 seed 估出的 std 本身不可靠（§26）。

> ⚠️ **四个侧特征是一起加的，个体贡献未归因。** author / tag / duration / video_age
> 同时进塔，没做逐个消融，所以「tail 的 +31.4% 来自哪一个」查不了。做这个归因需要
> 4 次额外训练 × 3 seeds。未做。

### 7.3 Negative Scale（独立实验：只改负样本数量）

§7.1 问的是负样本从**哪儿**来 —— 五臂，`negatives_per_positive` 一律 10（§16.6 把它列为
受控变量）。本节问的是有**多少**个，它**故意**动了那个受控变量，所以是独立的入口、
独立的汇总文件、独立的表。`src/evaluation/negative_sampling_analysis.py` 里有一处显式
`continue` 把这个实验臂挡在五臂表之外，那是同一个决定的另一半。

配置固定在当前最优组合（ID + Side 物品塔 + In-batch + logQ，§7.1 / §7.2），其余一切相同
（同 lr / batch_size=1024 / temperature / 20,000 步 / 同一组 seed / 同一候选库与考题集），
唯一的差别是 softmax 里有多少个候选：

| 实验臂 | 负样本位置 | 每行有效负样本 |
|---|---|---|
| `inbatch_logq`（基线） | 抽 10 个 in-batch target | 10（**来自 config，非实测**，见下） |
| `inbatch_full_logq` | batch 内其余全部 B−1 = 1023 个 | **1022.98 / 1022.99 / 1022.99**（3 seeds 首步实测） |

1023 只是上限：同一个 batch 里重复出现的 target 会按 ID 屏蔽掉（只屏蔽非对角位置，对角线
上的正样本保留）。实测重复占 12~18 个位置，于是有效负样本 1022.98 —— 相对基线 **102.3 倍**。

**结果：三层齐跌。** 3 seeds，mean ± std，按 request 平均：

| 实验臂 | Recall@50 | Recall@100 | Recall@500 | 倍热度基线(@100) | 末 100 步 loss |
|---|---:|---:|---:|---:|---:|
| **n_neg=10** | **0.00590±0.00032** | **0.01106±0.00040** | **0.04249±0.00068** | **2.26x** | 0.2460 |
| 完整 in-batch (1023) | 0.00438±0.00003 | 0.00815±0.00028 | 0.03236±0.00087 | 1.66x | 1.8446 |
| *Popularity 基线* | *0.00222* | *0.00490* | *0.02301* | *1.00x* | — |

| band R@100（倍随机猜） | tail | mid | warm |
|---|---:|---:|---:|
| n_neg=10 | 0.00456（8.9x） | 0.01038（20.2x） | 0.02151（41.8x） |
| 完整 in-batch (1023) | 0.00335（6.5x） | 0.00687（13.4x） | 0.01720（33.4x） |

配对差值（同 seed 相减）：

| 完整 in-batch − n_neg=10 | mean±std | 方向一致性 | `\|mean\|/std` | 相对基线 |
|---|---:|---|---:|---:|
| overall R@50 | −0.001518±0.000316 | 3/3 同号 | 4.8 | 0.743x |
| overall R@100 | −0.002916±0.000418 | 3/3 同号 | 7.0 | 0.736x |
| overall R@500 | −0.010130±0.000266 | 3/3 同号 | **38.1** | 0.762x |
| tail R@100 | −0.001205±0.000337 | 3/3 同号 | 3.6 | 0.735x |
| mid R@100 | −0.003509±0.000492 | 3/3 同号 | 7.1 | 0.662x |
| warm R@100 | −0.004310±0.000836 | 3/3 同号 | 5.2 | 0.800x |

**主结论：在同样的步数预算下，把负样本从 10 个加到 1023 个是净亏 —— R@100 相对下降
26.4%。** 六格全部 3/3 同号，`|mean|/std` 3.6~38.1，远强于本 README 里任何一项敢下结论的
离散度（§7.2 最干净的一格是 2.47）。倍热度基线从 2.26x 退到 1.66x。

**它不是一次 warm↔tail 的交易。** 三层近似等比例变弱（0.735x / 0.662x / 0.800x），相对
跌幅最大的是 mid 而非任何一端。这排除了「logQ 在 1023 个候选上过校正、把冷门推上来」
这条解释 —— 那样 tail 应该上升。

> **事先的机制预期是「重复一次 §7.1 里那场 warm↔tail 的交易」，被实测否掉了。**
> 这个预期**没有落盘** —— 不同于 §7.1 的 `results/logq_prediction.json`（跑之前写进文件、
> 事后逐条对账）与 §7.2 那条进了 git 的预测。所以它不具备那两者的对账资格，只作记录：
> 预期错了，实测是三层均匀变弱。

> ⚠️ **必须一并披露：实验臂在 20,000 步时没有收敛，这限定了结论的范围。**
> 它的 loss 到最后一刻仍在陡降（seed 42 的 step 14000 / 16000 / 18000 / 20000 =
> 2.3153 / 2.1407 / 2.0047 / **1.8453**，最后 2,000 步还降 8.0%，单调、无平台）。题从
> 「11 选 1」变成「1024 选 1」，同样步数、同样 lr，它走到的位置更靠前。
> 因此本节成立的范围是「**同 20,000 步预算下**」—— §16.6 把 `steps` 列为受控变量，这么跑
> 是对的；但它**支持不了**「负样本多了更差」这个更强的说法。
> 观测到的现象（三层近似等比例变弱、倍热度基线下降）与「这就是同一个模型练得更浅」完全
> 一致，而一致不等于证明：没有中间 checkpoint，这两种解释区分不了。能区分的实验是把完整
> in-batch 单独跑到 60,000 步、看它是否越过基线 —— 那会**故意**破掉 `steps` 这个受控变量，
> 因此是另一个问题、另一张表。未做。

> ⚠️ **`loss` 一列跨臂不可比，这次还差了一个量级。** n_neg=10 是 11 分类
> （随机猜 ln(11) = 2.398），完整 in-batch 是 B 分类（ln(1024) = 6.931）；归一化后是
> **0.103 vs 0.266**。完整 in-batch 的 loss 大 7.5 倍，是因为题从「11 选 1」变成了
> 「1024 选 1」，不是训练更差。结果 JSON 现在会同时落盘
> `negative_positions_per_positive` 与 `loss_tail_normalized`，就是为了三个月后翻
> `results/*.json` 的人不会把 1.84 读成「崩了」。**归一化量也不是 Recall 的代理** ——
> 判据只有上面那两张 Recall 表。

> ⚠️ **基线的 `n_neg=10` 来自 config，不是实测。** 那三份基线 JSON 产出于
> `negative_positions_per_positive` 这个字段加进 `two_tower.py` **之前**，而
> `configs/retrieval.yaml` 可以在跑完之后被改 —— 与 §7.1 末尾披露的是同一层缺口。
> 实验臂那一侧是实测的（上面的 1022.98）。汇总脚本对此会打 `WARNING`，并把
> `baseline_n_neg_from_config: true` 写进
> `results/negative_scale_summary_main_id_side.json`。要彻底补掉只有一个办法：用现在的
> `two_tower.py` 重跑基线 3 个 seed（约 2 小时）。未做。

#### 数量扫描：5 / 10 / 30 —— 区间内不敏感，而单 seed 筛选差点给出相反结论

1023 变差只证明「极多不合适」，推不出 20/30/50 也变差 —— 最佳点可能在中间。于是在同一
配置上补了两点。由 `python scripts/negative_count_analysis.py` 复现：

| 实验臂 | Recall@50 | Recall@100 | Recall@500 | 归一化 loss |

> `results/negative_count_prediction.json` 写于 2026-10-30 22:22:47，早于 seed 43/44 开跑，
> 里面锁了判据线、三条预测、一条证伪条件，以及一条**派给自己的失败预测**。对账由
> `negative_count_analysis.py` 自动打印，不靠人读：
>
> | 指标 | 预测 `\|m\|/std` | 预测过线 | 实测 | 实测过线 | 结果 |
> |---|---:|---|---:|---|---|
> | recall@50 | 2.4 | 是 | **0.09** | 否 | 错 |
> | recall@100 | 0.9 | 否 | 0.22 | 否 | 对 |
> | recall@500 | 3.6 | 是 | **0.18** | 否 | **错** |
>
> 证伪条件原文：「若 R@500 的配对差值在 seed 43 或 44 上变号，则 seed 42 的 3.6 倍是噪声，
> 结论改为『n_neg 在 5~30 区间内对所有指标都不敏感』」。seed 44 给出 **−0.001623**，变号，
> **条件触发**。三条过线判断只对了 1 条。
> 那条自派的失败预测（R@50 预计回落，因为基线在该列是 −0.93 sd 的低抽）成立：2.4 → 0.09。

**为什么 seed 42 单点看起来那么漂亮 —— 有机制，而且量出来了。**

| 跨 seed 离散度 | n_neg=10 | n_neg=5 | 比值 |
|---|---:|---:|---:|
| recall@50 | 0.00032 | 0.00084 | 2.6x |
| recall@100 | 0.00040 | 0.00104 | 2.6x |
| recall@500 | 0.00068 | 0.00226 | **3.3x** |

负样本越少，softmax 的梯度估计越糙，跨 seed 抖动越大。筛选时只跑了 seed 42，而量它的尺子
是从 n_neg=10 那组**较小**的离散度借来的 —— 用小方差的尺子量一个方差大 3 倍的臂，单点量出
「3.6 倍」几乎是必然。这个比值本身**不作结论**：3 对 3 个 seed 估方差比，自由度 (2,2)，
极不可靠。

> **loss 与 Recall 在这里公开吵架，这正好证实了上面那条写死的保留。** 归一化 loss 说
> n_neg=5 明确更好（**0.0982±0.0005 vs 0.1026±0.0012**，差 4%，离散度小一个量级），
> Recall 说是掷硬币（0.18 倍）。本节开头写的「归一化量**也不是 Recall 的代理**」因此不再
> 只是一句提醒，它有了实测案例：loss 很稳，但它稳在另一个量上。

> ⚠️ **方法教训：单 seed 筛选在高方差臂上会制造假信号，这次的具体数字是 3.6 倍 → 0.18 倍。**
> 分阶段筛选本身没错 —— 它确实挡掉了 n_neg=50（省 59 分钟）。错的是拿单点的倍数当
> 「明显超过」的证据。按本节实测的离散度，单 seed 能分辨的量级是 **8~17%**，而 5~30 区间内
> 的真实差异在 ±2% 以下：**这个筛选从一开始就没有分辨它要找的东西的能力。**

> ⚠️ **两处因这次扫描而收回的话。**
> ① 曾按 seed 42 的四个单点写下「R@500 在 5/10/30/1023 上严格单调递减，四点连成一条线，
> 把『没收敛』从保留变成有四点支撑的解释」。补齐 seed 后 5→10 这一段是 0.18 倍，顺序定不
> 下来，**单调只剩 10 → 1023 那一段**（那一段很硬，`|mean|/std` = 38.1）。上面那条收敛解释
> 仍然站得住，但支撑是 10 vs 1023 加 loss 轨迹，**不是一条单调的 n_neg 曲线**。
> ② 2/3 seeds 时曾读作「R@500 在变强」（seed 43 的差值比 seed 42 还大）。它没活过第三个
> seed。中途读数就是会这样 —— 这也正是预测必须先落盘的理由。

**n_neg=50 没有跑，理由是事先立的停止规则。** 筛选规则是「只有某个配置明显超过 10，才往上
扩」。n_neg=30 的单 seed 结果没过线（R@100 持平、R@500 更差，唯一的 R@50 优势后来被证明是
基线低抽的产物），而它是通往 50 的那一步。规则事后可以改，但得有新证据，这次给出的证据是
反向的。

**代价（四个实测点）。** 每步成本随 n_neg **明显次线性**，不能用单一边际成本外推：

| n_neg | seeds | 行/步 | ms/step | 分钟/seed | 来源 |
|---|---:|---:|---:|---:|---|
| 5 | 3 | 6,144 | 112.4 | 37.5 | 正式跑实测 |
| 10 | — | 11,264 | 127.0 | 42.3 | 200 步烟测 |

| 完整 in-batch (1023) | 3 | 16,384 | 140.7 | 46.9 | 正式跑实测 |

边际成本从 **2.84 μs/行**（6,144 → 11,264）降到 **1.22 μs/行**（11,264 → 31,744），差 2.3 倍
—— 大矩阵乘的吞吐更高。每步约 **79%** 是与 n_neg 无关的固定开销：Adam 要更新
**172,998,572** 个参数，其中 item embedding 占 **33.2%**（57,440,320）。按后两点的斜率外推，
n_neg=50 约 **177 ms/step ≈ 59 分钟/seed**，仍比完整 in-batch 的 46.9 分钟贵 ——
**102 倍负样本比 50 个便宜**这个结论不变。

> **这个数字换过一次。** README 早期写的是「n_neg=50 约 223 ms/step ≈ 74 分钟」，那是用
> n_neg=10 与完整 in-batch 两点标出的单一边际成本（2.344 μs/行）外推的，**偏高 26%**。
> 两个点标不出曲率；现在有四个实测点，上表取代了那次外推。

| is_like | 28,736 | 2.70% | −0.00400 | −0.000108 |
| is_comment | 4,866 | 0.46% | −0.00716 | −0.000033 |
| is_follow | 1,457 | **0.14%** | −0.01180 | **−0.000016** |

点击与长播占 96.7% 的权重，is_follow 只占 0.14%：MMoE 在 follow 上 −0.0118 的损失被稀释
700 倍后只剩 −0.000016，等于消失。而关注 / 评论**恰恰因为稀少才珍贵**，按频次加权等于把
权重和业务价值搞反。工业上的做法相反 —— PLE 线上的排序分是
`score = p_VTR^w_VTR × p_VCR^w_VCR × ... × p_CMR^w_CMR × f(video_len)`，那些 `w` 是按线上
实验调出来的**业务权重**，不是频次。离线拿不到业务权重，所以**逐任务报是唯一诚实的做法**。

MMoE / PLE / STEM 三篇论文也都逐任务报，没有一篇报聚合指标。

#### 核心发现：共享机制与任务稀疏度的权衡，不存在总冠军

四个 MTL 模型在 **ΔAUC 的三个稀疏任务上全部是 3/3 seed 同号的负迁移**，没有一个例外；
差别只在幅度与代价分布：

| | 稠密任务收益（ΔAUC click / long_view） | 稀疏任务损失（ΔAUC like / comment / follow） |
|---|---|---|
| MMoE | +0.0014 / −0.0005 | −0.0040 / −0.0072 / −0.0118 |
| CGC | +0.0031 / +0.0030 | **−0.0026 / −0.0057 / −0.0103** |
| PLE | +0.0008 / +0.0019 | **−0.0026 / −0.0056 / −0.0098** |
| **Selective Sharing** | **+0.0042 / +0.0035** | −0.0030 / −0.0063 / −0.0123 |

读法是**不同共享结构对应的经验权衡**，而不是把四种架构排成单一的“共享强度”或总排名：

- **CGC / PLE 的负迁移幅度最小。** 相比 MMoE，is_like 的损失从 −0.0040 缩到 −0.0026，
  is_comment 缩小约 22%，与 PLE 关于任务专属专家缓解有害干扰的主张一致。但模型之间还同时
  改变了专家宽度和容量分配，因此这是本设置下的观察，不是只归因于共享机制的因果证明；
  而且负迁移并未消除，三个稀疏任务仍全部劣于 Single-Task。
- **Selective Sharing 的稠密收益最大、代价也最集中。** 它在 click / long_view 上的
  ΔAUC（+0.0042 / +0.0035）是五个模型里最高的，std 只有 0.0004~0.0005；但在 GAUC 上
  is_follow 掉到 **0.48554**，是唯一**跌破随机**的模型（ΔGAUC −0.02469，3/3 同号）。
- **CGC 与 PLE 在三个稀疏任务上分不出高下。** 直接配对的 `PLE−CGC` ΔAUC 为：is_like
  +0.00006±0.00094、is_comment +0.00018±0.00199、is_follow +0.00052±0.00643。多层
  progressive routing 在这些任务上没有可测增量。原因可能与第二层容量或可路由信息有关，
  但没有加宽 / n_levels 消融，不能把机制猜测写成结论。

**机制上说得通的解释**（仍是假设，不是已证实的因果）：共享学习面对严重的任务梯度不平衡。
下面是 **MMoE** seed 42 checkpoint 在 8,192 行 batch 上对 `experts.*` 测得的逐任务梯度范数，
不是 Selective 的专属测量：

```text
long_view  0.068560  35.6x      is_like     0.004734   2.5x
is_click   0.042889  22.3x      is_comment  0.002121   1.1x
                                is_follow   0.001924   1.0x
```

它证明共享路径接收到的任务信号很不平衡，也为 Selective 的结果提供了一个候选解释：虽然
各任务的 gate 彼此独立，但共享的 RankingEncoder 与 shared expert 仍同时接收所有任务梯度，
因此可能更偏向稠密任务。**它不能直接证明 Selective 的 32 维私有分支太小**；确认这一点还需
对 Selective 的 shared/private/gate 分别测梯度，并做私有维度消融。当前可以下的结论仅是：
“可选择的共享”没有天然消除负迁移，在本设置下反而出现了最清楚的稠密/稀疏两极分化。

注意 loss 值**不是**梯度的好代理：loss 最大的是 is_click（0.57976，是 follow 的 87 倍），
梯度最大的却是 long_view，连顺序都不一样。早先版本用 loss 倍数直接推因果，方向碰巧对但
证据链不成立。

**这不是实现缺陷，而是文献中有名字的现象**：PLE 称之为 seesaw phenomenon，其 Table 1 中
MMoE 相对 Single-Task 是 VTR +0.0016 / VCR −0.0001（一正一负）；MMoE 原论文 Table 1/2 中
MMoE 赢主任务、输辅助任务；STEM (AAAI-24) Figure 1 显示在两任务反馈量相当的样本子集上
MMoE 与 PLE 均劣于 Single-Task。本项目在五个任务、四个 MTL 模型、3 seeds 上复现了它。

> ⚠️ **单 seed 的符号排列极易自圆其说，这里有过一次教训。** seed 42 单看时 MMoE 的五个
> 任务符号"完全按稀疏度分开"（两个稠密为正、三个稀疏为负），与等权 loss 的机制完美吻合。
> 3 seeds 之后 long_view 变为 −0.00045（不显著），说明"稠密受益"这一半当时只有 is_click
> 成立。**在符号结构上做解释之前必须先补 seed。**

#### 效率：MTL 的确定收益在这一侧

| Model | 训练时间（3-seed 平均） | 总参数 | dense 参数 | 部署权重 |
|---|---:|---:|---:|---:|
| Single-Task | 14.36 分钟 | 188.01M | 620,805（5×124,161） | **5 套** |
| MMoE | 8.64 分钟 | 38.46M | 981,285 | 1 套 |
| CGC | 8.51 分钟 | 38.27M | 795,069 | 1 套 |
| PLE | 12.82 分钟 | 38.63M | 1,149,715 | 1 套 |
| Selective Sharing | **5.53 分钟** | 38.40M | 925,189 | 1 套 |

四个 MTL 变体的总参数**相对 MMoE 各自都相差不到 0.5%**（四者最大跨度约 0.93%；
Selective 的 dense 是 MMoE 的 0.943，构造时强制检查）。Single-Task 的 embedding 是 5 份，
所以它是**参照点而非预算内的一档**。

但**总参数接近不等于计算量接近**：MMoE 是 8 个宽专家，PLE 两层合计 28 个窄专家，FLOPs 与
访存模式不同，所以训练时间必须实测报告，不能由参数量推断（3-seed 平均下 PLE 比 MMoE
慢约 48%）。

工业动机也在这一侧：线上部署的是**一套权重同时服务多目标**（PLE 论文 §3.1 的排序分是
`p_VTR^w × p_VCR^w × ... × f(video_len)` 的融合）。五个独立模型并非技术上不能部署，
但参数、计算、版本管理与跨目标一致性的成本都明显更高。MMoE 原论文 §6.4 也指出分开训练
每个任务会显著扩大参数规模，而 Shared-Bottom 已在生产中使用。
**Single-Task 是尺子，不是候选方案** —— 但"负迁移"只有相对不共享才有定义，所以它必须
留在表里。

#### seed 方差随稀疏度暴涨，决定了哪些任务能下结论

Single-Task 的 3-seed std（本项目第一次真实测量）：

| | is_click | long_view | is_like | is_comment | is_follow |
|---|---:|---:|---:|---:|---:|
| AUC std | 0.00047 | 0.00060 | 0.00093 | 0.00053 | **0.00901** |
| GAUC std | 0.00091 | 0.00078 | **0.00751** | **0.00968** | 0.00226 |

对照文献的效应量（+0.0016~+0.0045）：稠密任务的 Single-Task seed std 较小，而 is_follow
的 AUC std 达到 0.00901。使用正确的配对差值后，MMoE 的 is_follow ΔAUC 是
−0.01180±0.00543、3/3 seed 为负；它提供方向一致的证据，但 3 个 seed 仍不足以做显著性判断，
绝对 GAUC 又只基于 395 个用户。增加 seed 能改善跨 seed 均值估计，增加用户与每用户正样本
才能直接改善稀疏 GAUC 的测量能力，因此正式结论仍需 27K 复核。

**GAUC 的 seed 方差在部分稀疏任务上比 AUC 大一个数量级**（is_comment 0.0097 vs 0.0005），
所以 MMoE / CGC / PLE 的多数细微 ΔGAUC 读不出；例外是 PLE 的 long_view，以及效应量更大的
Selective。GAUC 在度量意义上更贴近用户内排序，但在 1K 上只有足够大的效应才能越过噪声。

> 方法论备注：诊断阶段曾用「单次训练内部、各评估点之间的波动」当作噪声尺度的代用品，
> 实测它系统性**高估 4~8 倍**（is_click AUC：代用品 0.0036 vs 真实 seed std 0.00047）。
> 它量的是优化过程的抖动，收敛后会被平均掉，与 seed 方差不是一回事。显著性判定只能用
> seed std。

#### PCOC：共享让最稀疏的任务明显失准

```text
is_click    1.1078 -> 1.0390   改善
long_view   1.1952 -> 1.1168   改善
is_like     1.3866 -> 1.3798   基本不变
is_comment  1.9317 -> 2.1529   恶化
is_follow   1.9356 -> 2.7168   明显恶化（高估从 94% 升到 172%）
```

AUC 只看排序不看数值，抓不到这件事。共享表示让稀疏任务**失准而非失序**正是 §28 负迁移
分析的抓手。以 MMoE 为例，is_follow 的 ΔAUC 在 3 seeds 上方向一致，ΔGAUC 方向不一致，
而 PCOC 的恶化幅度远超其他任务。

#### 一个尚未解耦的混杂因素

本项目的 Single-Task 是 **5 张独立 embedding 表**，MMoE 是 **1 张共享表**。因此
ΔAUC(MMoE − ST) 同时混了两个变量：(a) 专家 / 塔是否共享；(b) **embedding 是否共享**。
STEM (AAAI-24) 的核心论点正是 (b) 才是负迁移主因 —— 现有 MMoE / PLE 都属于
shared-embedding paradigm，该文为此专门构造 ME-MMoE / ME-PLE 来分离这两个变量。
§25 的 Selective Sharing 若在 **embedding 层**也设一档（如稀疏任务给专属 embedding），
即可同时覆盖这个前沿方向。

- **稀疏任务的高 AUC 主要来自用户之间的差异，不是「这个视频值得关注」。**
  Single-Task 的 is_follow AUC 是 0.816 而 GAUC 只有 0.510 —— 绝大部分判别力来自模型学会了
  「哪些用户爱关注」，而不是「什么视频值得关注」。若只看 AUC 会得出「follow 比 click
  做得好得多（0.83 vs 0.74）」这个完全错误的结论。因此研究问题二真正要看的是
  **GAUC**，而不是 ΔAUC 的绝对值。
- **Single-Task 的 PCOC 随稀疏度总体恶化**：1.108 → 1.195 → 1.387 → 1.932 → 1.936。
  最稀疏的两个任务把概率高估约 94%。AUC 只看排序不看数值，抓不到这件事 —— 而共享表示
  最可能让稀疏任务
  **失准而非失序**，这是 §28 负迁移分析的抓手。
- **GAUC 参与用户数必须与指标一起报**：985 → 982 → 780 → 452 → 395。标签恒定的用户
  AUC 无定义，一律排除；follow 上只有 40% 的用户可算。

#### User x Author 偏好特征把 follow 拉离了「随机」这条地板

最初的基线里 is_follow 的 GAUC 是 **0.49014**、is_comment **0.50537** —— 用户内部排序与
随机无异。原因是模型完全没有 user x author 交互特征：用户侧只有历史视频的**池化均值**，
物品侧只有作者 embedding，靠 MLP 反推「是否同一作者」极难。实测一个计数特征
（该用户过去 7 天看该作者几次）单独的 GAUC 就有 0.53784 / 0.53764 —— **打赢整个 3,750 万
参数的模型**，证明信号存在、只是没进输入。

补上 §8.4 之后（seed 42 特征消融；15 列，窗口 3/7 天，T-1 口径）：

| task | ΔAUC | **ΔGAUC** |
|---|---:|---:|
| is_click | +0.00134 | +0.00455 |
| long_view | +0.00389 | +0.00410 |
| is_like | +0.00210 | +0.00516 |
| is_comment | +0.00029 | +0.00810 |
| **is_follow** | **−0.00056** | **+0.02211** |

**is_follow 的 AUC 降了、GAUC 升了 0.022** —— 改善完全发生在用户内部。若特征只是让模型
更会判断「哪些用户爱关注」，AUC 会涨而 GAUC 不动；实际方向相反。ΔGAUC 的梯度也符合
预期：稠密任务 +0.004~0.005，follow +0.022（五倍）。

仍要披露的两点：

- **follow 远没解决。** 3-seed Single-Task 均值 0.51024 只是勉强高于随机，而且
  `ua_imp_7d` 单特征的 0.53784
  **仍然高于加了该特征的整个模型**。3,750 万参数没把这 15 列用好（74% 的行没有近期
  历史、取先验值；embedding 可能在别处过拟合把信号淹了）。这个缺口恰好是研究问题二
  的一个具体假设：共享表示若真能帮稀疏任务，应表现为它把这些列用得比 Single-Task 更好。
- **PCOC 在两个稀疏任务上恶化**（1.827→1.962、1.823→1.912）。排序变好、数值更偏。

口径偏离（都由实测驱动，写在 configs/data.yaml 的 `pair_preference` 注释里）：窗口不取
1 天（(user,author,date) 日表 8,371,862 行而原始日志 9,015,279 行，平均 1.08 次/三元组，
1 天窗口对约 96% 的样本恒为 0）；只给 is_click / long_view 算平滑比率（pair 维度曝光量
0~4，给 0.11% 的事件算比率是纯噪声）。缺历史时计数填 0、平滑比率填**全局先验 g** ——
平滑公式在 num=imp=0 处恰好等于 g，填充与公式天然一致。

#### 物品侧在测试期几乎是空的

排序训练在曝光日志上，而本数据集内容换代极快（72.6% 的视频在 31 天窗口内上传）。
实测测试段的物品侧覆盖率：

| 标签 | 时长 | 上传日期（→ video age） | 作者 | **目标视频 ID** |
|---:|---:|---:|---:|---:|
| 96.6% | 93.3% | ~100% | 64.1% | **10.8%** |

视频 ID 有 89.2% 对不上，这**修不了也不该修**：昨天刚上传的视频不可能有学过的专属向量。
模型从「不知道是什么」变成「不知道是哪一个，但知道谁拍的、什么类、多长、多新」——
这正是真实系统处理新视频的方式。为此排序侧单独建了一张物品元数据表（只用合法的 basic
元数据，官方统计表全表禁用），三个词表全部只由 train 段构建，召回侧文件一个字节未改。

#### 一条已修的捷径，一条残留的漂移

**已修**：目标视频 ID 最初沿用召回词表，而召回词表 =「候选库 ∪ train 段正向视频」——
成员身份**部分由训练标签决定**。实测 train 段 962,054 条 OOV 样本里 is_click 与 long_view
的正样本率**恰好为 0**（任何正样本都会把该视频送进词表），于是「在词表内」这一个比特
单独就有 train AUC 0.6981 / test 0.5190。is_like 不受影响（0.5043），因为召回词表的
positive_signal 只含 is_click 与 long_view —— 机制完全对得上。目标通道已换成只由 train
曝光次数构建的词表（194,310 个，与候选库逐个相同）；历史通道仍用召回词表，两者各一张
embedding 表。

**残留（披露而非掩盖）**：新的 `video_id_known` 仍带轻微热度信号，train 0.5509 /
valid 0.5248（强度差 0.026）。它是合法的 prediction-time 特征（train 期曝光相对 test
是过去数据），但差距不为零。对比修复前的 0.179，性质不同。验算里有一层常设的**捷径
扫描**：先实测哪些通道真的进了模型，再比 train/valid 单特征 AUC 强度，超 0.15 报错、
0.05~0.15 逐条打印披露。

#### 过拟合位置与训练预算

原设置（5 轮、无正则）下 valid AUC 从第 1 轮起单调下滑，is_follow 更是从峰值掉 0.0915。
逐个消融后定位到**历史 embedding**（897,505 行 × 32 = 2,870 万参数，占 77%）：

| 手段 | 打在哪 | is_click 1 轮末 AUC | 有效 |
|---|---|---:|---|
| 基准 | — | 0.72780 | — |
| dropout=0.2 | 塔（12 万参数） | 0.72734 | ✗ |
| id_dropout=0.3 | 目标 ID（620 万） | 0.72864 | ✗ |
| 去掉整条目标 ID 通道 | — | 0.72817 | ✗ |
| lr 1e-3 → 3e-4 | — | 0.72503 | ✗ 更差 |
| **weight_decay=1e-5** | **全部 embedding** | **0.73372** | ✓ |

预算（epochs=1 / weight_decay=1e-5）一次性在 **valid** 上选定，五个模型共用同一套值，
完整依据写在 `configs/single_task.yaml` 的注释里。取 1e-5 而非 1e-4 是因为后者在 is_follow
上掉 0.024 —— 只看 is_click 会选错。顺带结论：目标 ID 通道对 valid AUC 的贡献≈0（拿掉
只动 0.0004），与它在 test 段 89.2% 是 OOV 一致；保留它是为了与 MTL 对比时结构一致。

#### 一个必须披露的不对称

Single-Task 是 5 个**完全独立**的模型（不共享 embedding），MMoE / CGC / PLE / Selective
各是 1 个模型带 5 个头。因此总计算量与参数量都差约 5 倍 —— 这是「共享 vs 不共享」这个
比较的固有形态，不是算力对齐实验。§25.1 里 Single-Task 是**参照点**，参数预算可比性只在
四个 MTL 变体之间要求。

**checkpoint 选择必须对称**：ST 可以为 5 个任务各挑一次最佳轮，MTL 只能挑一次；若允许
ST 挑 5 次，ΔAUC 会系统性偏向 ST、凭空造出负迁移。因此五个模型一律**固定轮数、报最后
一步**，每 500 步记曲线但不据此选择。

### 7.5 Controlled Label Sparsity

正样本整行下采样至 100% / 10% / 1% / 0.1%，固定架构、特征、用户集、时间切分与种子，
只改变可用正向训练信号，观察各共享机制的 ΔAUC 与负迁移敏感性。

## 10. Scope Guardrail

Retrieval P0 只含 ItemCF + Two-Tower + 五个负采样实验臂（另有一项独立的负样本**数量**实验，
§7.3，它故意动了 §16.6 的受控变量，因此单独成表）+ ID-only / ID+Side 两个物品塔
+ Recall/NDCG 评估。**不含 candidate
union** —— 每一路召回独立评估，理由见 §2。全库检索用**精确的分块暴力**而非 ANN：
19.4 万候选暴力只要 13.3 秒，而 ANN 的近似误差会混进各策略的对比里（§16.6 要求
除采样外无任何差异）。在多任务主线（MMoE / CGC / PLE / Selective Sharing /
Controlled Sparsity / 3-seed）全部完成前，**不新增** popularity / author / tag / freshness
等启发式召回源，也不新增第二个协同过滤基线（UserCF 已作一次性诊断，结论见 §7.1）。时间预算约为
data 25% / retrieval 25% / MTL 35% / analysis 15%。
